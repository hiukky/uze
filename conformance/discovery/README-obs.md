# UZE — Harness Conformance: Real Harness + Synthetic World

Smallest permanent architecture that proves UZE-relevant harness behavior with
the **real** harness binary and a **synthetic** external world — no OAuth, no
Google/Cloud account, no real provider, no tokens, zero external Internet.

This is not "replay". We do not model Google OAuth, Cloud Code PA, Unleash,
userinfo, quota, experiments, telemetry, update, or Playwright endpoints — the
API-key/offline path proved they are unnecessary.

**Validation priority (per decision):** TUI slash-command surfaces wherever the
harness offers them; CLI/state only when no TUI surface exists.

## Run (final minimal scenario, 3x, clean state, no external network)

```bash
python3 -m venv /tmp/mitm-venv && /tmp/mitm-venv/bin/pip install pexpect
/tmp/mitm-venv/bin/python runtime/scenario.py --harness antigravity 1
/tmp/mitm-venv/bin/python runtime/scenario.py --harness claude 1
/tmp/mitm-venv/bin/python runtime/scenario.py --harness codex 1
# ... repeat per run index; 3x per harness verified, zero flakes
```

Each run recreates the `--internal` network + provider + harness containers
from clean state and writes `verdict.json` + screen evidence under
`/tmp/harness-conformance/<harness>/run<N>`.

## Protocol facts this test relies on (all observed from the real binaries)

### Antigravity 1.1.20
- **Synthetic auth**: `modelProvider: "gemini"` in
  `~/.gemini/antigravity-cli/settings.json` + `GEMINI_API_KEY` → OAuth
  bypassed; credential row shows `Gemini API key`.
- **Provider redirect**: `GOOGLE_GEMINI_BASE_URL` → model request lands on the
  stub (`/v1beta/models/{model}:streamGenerateContent?alt=sse`).
- **SSE framing**: AGY's parser fails on a `data: [DONE]` terminal — the
  response must be `data: {json}` lines only (this also resolved the old
  interactive agent-loop error).
- **MCP tool call**: generic `call_mcp_tool`, args camelCase
  `serverName`/`toolName`/`arguments`; MCP execution needs an allow-rule
  (`permissions.allow: ["mcp(*)"]`).
- **TUI surfaces**: `/skills` (skills incl. plugin + global), `/mcp` (MCP
  servers with a "Plugins" source section). **Plugins have NO TUI surface**
  — validated via CLI (`agy plugin list`).

### Codex (codex-cli 0.149.1)
- **Auth**: `~/.codex/auth.json` with a dummy key
  (`{"OPENAI_API_KEY":"sk-dummy-l2t-bypasses-onboarding"}`) skips the login
  screen; the directory-trust prompt is dismissed with Enter.
- **Endpoint**: codex first attempts `wss://api.openai.com/v1/responses`
  (WebSocket). A clean WS close makes it fall back to HTTPS
  `POST /v1/responses` (OpenAI Responses API, SSE events). TLS interception
  via /etc/hosts + `CODEX_CA_CERTIFICATES`/`SSL_CERT_FILE`.
- **TUI surfaces**: `/skills` (Choose an action -> Enable/Disable),
  `/plugins` (Installed list), `/mcp` (MCP inventory).
- **Honest findings (never a pass)**: with the current UZE delivery the
  plugin skills are absent from codex's model catalog (only built-ins) and
  the UZE MCP config does not reach the /mcp inventory.

### Claude Code 2.1.245
- **Auth**: `ANTHROPIC_API_KEY` (dummy) → "API Usage Billing" mode; the TUI's
  first-run API-key dialog must be answered Yes (Up+Enter).
- **Preflight**: the interactive TUI hardcodes connectivity checks against
  api.anthropic.com, platform.claude.com, console.anthropic.com,
  statsig.anthropic.com, api.statsig.com, sentry.io, telemetry.anthropic.com.
  Solved synthetically: `/etc/hosts` + a TLS provider (cert with all SANs,
  signed by a per-run CA) + `NODE_EXTRA_CA_CERTS`. `ANTHROPIC_BASE_URL` is
  ignored by the interactive TUI — the TLS interception is the required hook.
- **Model protocol**: `POST /v1/messages` (stream=true), Anthropic SSE events
  (message_start/content_block_start/delta/content_block_stop/message_delta/
  message_stop).
- **Onboarding drive**: theme → API key (Yes) → security notes → trust
  (cursor already on Yes) → Tips/"What's new" popup (auto-dismissed by the
  first slash keystroke; **never send Esc** at the empty prompt — it exits).
- **TUI surfaces**: `/plugin` (Installed/Marketplaces/Errors) and `/mcp`
  (servers, ✔ connected · tools) — both validated in the TUI.
- **Skills have no human TUI surface** in 2.1.245 (no `/skills` slash); the
  skill surface is model-facing (the `Skill` tool + system-reminder listing).

## Known PARTIALs (documented, never a pass)

- **Claude MCP execution inside the conversation**: claude defers MCP tools
  behind ToolSearch (deferred-tool protocol); a direct `mcp__` tool_use fails
  with "No such tool available". Registration + connection are proven via the
  `/mcp` TUI surface; tool execution needs the ToolSearch protocol modeled.
- **Claude auxiliary skill-list leak**: a no-tools auxiliary request includes
  the full skill listing; the primary model request is clean.

## Adding the next harness

1. Locally: use `discovery/` (mitmproxy + host observation) to learn the new
   harness's synthetic-auth + provider-redirect hooks.
2. Distill into `runtime/fixtures/<new-harness>/` (settings/state seeds,
   deterministic response) and, if needed, a new `runtime/providers/` backend.
3. Extend `runtime/scenario.py` with the harness's setup + TUI assertions.
4. Run 3x offline; the harness is green when its matrix row is PROVEN.
