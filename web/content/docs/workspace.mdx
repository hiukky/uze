# The agent workspace

Running `uze` with no arguments opens the **workspace**: a persistent terminal
that hosts your agent sessions. A space decides how its agents work: in a
**worktree** space every agent gets an isolated checkout of the repository, so
two of them can work at the same time without touching each other's files — or
yours; in a **workspace** space the agents work in the space's own directory,
on the branch you are on, beside you.

<Callout type="info">
  The workspace is **experimental** (ADR-038). The runtime, its protocol, and the
  shortcuts below may still change.
</Callout>

## Spaces, tabs, panes

Three levels, and no more:

| Level | What it is |
| --- | --- |
| **Space** | One directory you work in — see [An agent is isolated, or it works where you work](#an-agent-is-isolated-or-it-works-where-you-work). The sidebar lists them; `+ new` (or `Alt+S`) opens a picker to add one. |
| **Tab** | One session inside a space — a plain shell, or an agent. |
| **Pane** | The live terminal a tab draws. Owned by the runtime server, not by the client. |

A shell opened while an agent is in front of you belongs to that agent: it
starts in the agent's own checkout, is shown with it, and **closes with it**.
A space keeps its own shells — the one it opened with, and any opened with no
agent selected — and closing an agent never touches those. This is what keeps
a closed agent's slot from being held open by a pane standing inside a
checkout on its way back to the pool.

The panes belong to a local server, not to the window you are looking at
(ADR-038). Closing the client — switching to management, detaching, quitting the
terminal emulator — leaves every process running; the next attach finds them
exactly where they were.

```bash
$ uze                    # attach the workspace (starts its server when needed)
$ uze terminal attach    # the same thing, explicitly
$ uze terminal stop      # stop this workspace's session and its processes
```

Running `uze` *inside* one of the workspace's own panes doesn't nest a second
client — it opens a space for that directory in the uze already running, and
exits.

## The conversation comes back too

The server outlives its client, but not the machine. After a reboot, a logout or
a killed process, the next `uze` brings the spaces, tabs and agents back — each
relaunched in the checkout it was working in, and each resuming the session it
was in rather than starting a stranger in a directory full of half-done work.

The decision is made when the process starts, in the shim `uze setup <harness>`
installs. The shim's presence is what turns this on and removing it turns it off;
nothing recreates it behind your back. A conversation is remembered per task and
per harness in uze's own state, never inside a checkout — so resetting or
deleting a checkout cannot take it, and a recycled slot starts its next task
fresh.

What ties a process to its task is the launch, not the directory: an agent uze
starts carries its identity in the pane's environment, the shim resumes by that
identity, and it verifies it against the task's own checkout before it does. A
harness you start by hand — in a shell tab, even inside an agent's checkout —
carries no identity and starts exactly as it would without uze. So does a harness
an agent starts from inside its own session: it never resumes the agent's
conversation.

Where it cannot be done — no shim, or no resume mechanism uze can drive — the
agent still starts and the tab says why. The [harness matrix](/docs/harnesses)
has the per-harness column.

## Shortcuts

| Keys | Action |
| --- | --- |
| `Ctrl+T` | New shell tab |
| `✦` (tab strip) | New agent tab — pick which harness starts |
| `Ctrl+W` | Close the selected tab |
| `Alt+1` … `Alt+9` | Select a tab by position |
| `Ctrl+G` | Open the changes overlay for the active tab's directory |
| `Alt+I` | Deliver the selected task |
| `Alt+Shift+I` | Deliver every ready task in the space |
| `Alt+P` | Preserved work — tasks whose agent is gone but whose branch still holds commits |
| `Ctrl+O` | Switch to management (and back) |
| `Ctrl+Q` | Quit |

Everything else typed goes to the pane. Tabs and spaces can be renamed inline
and reordered by dragging; right-click gives the same actions as a menu.

## An agent is isolated, or it works where you work

A space is a directory you opened uze at, and nothing more. Every agent you
start in one begins **where the project says**, and any single agent can be
given a checkout of its own afterwards — `Isolate`, on the agent's own row.

| Where an agent works | What uze does with its work |
| --- | --- |
| **In the space's root**, on whatever branch it is on | Nothing: the commits are already on your branch |
| **Isolated**, in a checkout of its own under `.worktrees/<id>`, on branch `agent/<id>` | Readiness, delivery and naming, as described below |

An agent in the root shares one tree with everyone else there, the way two
people in a shell would; uze keeps their conversations apart, and nothing
else. The column draws the two apart: the agents in the root first, then the
isolated ones under a blank row, each group in its own hue.

An agent's row says two things: the name of the work, and underneath it the
harness running it — `claude`, `codex`, `agy`. Not the branch: a named task's
label *is* its branch read as words, and every agent in the root shares the
operator's branch, so the caption repeated what the row already said. Where
the work lives is the space's, said once — on the header, behind the `⇄` that
swaps the space's name for its root, and in the timeline below.

### Isolate

`Isolate` is on an agent's right-click menu, and it is offered only where it
can be honoured: the space has to be a Git repository with a commit to branch
from, and the agent must not already have a checkout. It keeps the agent's
identity, its tab and its place in everything uze records about it; the
harness is relaunched in the new checkout.

Whether the *harness's own* conversation follows is up to the harness. One
that keeps a conversation under the directory it ran in — Claude Code does —
cannot resume it somewhere else, so the agent picks up in the new checkout
with a fresh conversation. Isolate early if the thread matters.

**Isolate** takes your uncommitted work with it — edits to tracked files and
new files git isn't ignoring alike. A copy: your own tree is exactly what you
left it. That is the default because what the tree holds when you move an
agent is usually what *that agent* was doing, and a checkout without it is one
where the file it was mid-edit on went back to its last commit.

**Isolate clean** stands beside it when your tree has uncommitted work, and
cuts the checkout from the last commit instead — the changes stay where they
are. It is the row for the case uze cannot see: a tree dirty from something
other than this agent. On a clean tree there is nothing to decide, so only the
one row is there.

## An isolated agent gets its own checkout

In any Git repository with at least one commit, uze places an isolated agent in
a checkout of its own **before its harness starts** — nothing required of the
harness. The primary checkout stays yours.

- The checkout is a **slot**: `.worktrees/<id>`, on branch `agent/<id>`.
- A new agent takes a **free slot** — new branch from the base, tracked and
  untracked files reset, ignored artifacts (a `target/`, a `node_modules/`) left
  in place — and a new directory is created only when no slot is free. The number
  of checkouts is bounded by peak concurrency, not by how many tasks you run.
- Where a slot cannot be acquired (no commit yet, the slot cap reached, Git
  refusing), nothing moves and the reason is said — an agent you asked to
  isolate never lands in your own tree.

Because the slot is reused, the second agent in a Rust project doesn't pay for a
cold build the way a fresh `git worktree` would.

<Callout type="warn">
  A `.worktrees/` slot is UZE's. Don't hand-manage the branches inside it — the
  workspace resets a slot when it hands it to the next agent.
</Callout>

### What the project declares

One block in `agents.yaml`, at the project root, and it is the primary checkout
that owns it — a worktree's own manifest is ignored:

```yaml
worktrees:
  default: in-place        # in-place | isolated — where an agent launched here starts
  target: main             # branch finished work targets (default: the primary's branch)
  completion: handoff      # handoff | merge | pr
  branch: conventional     # the vocabulary an agent's own name for its work is judged against
  link: [.env, .env.local] # ignored files a fresh slot links from the primary
  setup: pnpm install      # prepares a slot after linking; a failure warns, never blocks
  gate: cargo test         # run on the rebased commits; non-zero refuses delivery
  slots: 3                 # cap on concurrent checkouts (default: peak concurrency)
```

`setup` and `gate` each take one command or a list run in order — the list is
what makes a failure say which step failed. See the
[`agents.yaml` reference](/docs/project-files#worktrees) for the rest.

## The agent names its work

`agent/<id>` tells a reviewer nothing, and nothing uze knows at launch can do
better — the work has not been decided yet. The party that knows what it is,
is the agent doing it, so the agent says so, as its **first action**, before
it reads a file or plans anything:

```bash
uze agent task name fix/branch-naming
```

The branch becomes `fix/branch-naming` and the label beside it in the sidebar
reads `branch naming`: one name, authored once, for the two people who read it
— the reviewer meeting the pull request, and you reading three agents in a
strip. There is no identifier argument, so the task named is always the one
whose checkout the command ran in and no agent can rename another's work.

The moment is half the rule. A name states an *intention*, which the agent
holds from the request you gave it; nothing it reads afterwards makes the name
easier to choose, while any later moment is one it meets with work already
under way and weighs against the work. So it is the first thing the
"Concurrent work isolation" section projected into your `AGENTS.md` asks for.

Two mechanisms catch what that misses, and neither asks a harness for
anything:

- **Work that reaches a commit still unnamed** is named from that commit's
  subject, on the pass that already evaluates the task — judged against the
  same vocabulary. It reads `feat/answer-ping-with-pong` where an agent would
  have chosen two words, which is exactly what the projected instruction warns
  it will.
- **A published branch never carries the identifier.** A task nobody named at
  all is pushed under a name derived from its first commit.

**A name nobody generated is never overwritten.** Rename a branch by hand with
`git branch -m` and uze adopts it at the next evaluation — the sidebar,
delivery and the sync count all read the new one — and nothing automatic
renames it again.

**Asking renames, however often you ask.** An intention stated before reading
anything is often the wrong one, so the agent runs the same command again and
the branch follows; the last name given is the one that stands, and the name
it carried before is not left behind for a reviewer to find. Naming it what it
is already called is not an error either, so an agent can state its branch's
name without first asking Git what it is.

### The vocabulary is yours to close

A proposed name has to be validated, and only a closed set can be. `branch:`
takes a preset — `conventional`, `gitflow`, `flat` — or your own list of
types, which is the answer when a preset almost fits: a team that wants `ui`
declares `ui` rather than mislabelling the work as `style`.

```yaml
worktrees:
  branch: [feat, fix, docs, ui]
```

Undeclared, it is `agent`: work is not named, the branch stays the generated
identifier, and everything above is off.

## Readiness is read, not announced

Where an agent's work stands comes from Git in the checkout it sits in —
never from something the agent claims.

Every agent has one. An isolated agent has a checkout to itself, so the
answer is its own; agents working in the project's root share one with you
and with each other, and all read the same answer, which is the truth
about where they are. What only an isolated agent has is a branch UZE cut,
and therefore a delivery UZE may run — so the deliver button is drawn for
those alone:

| State | What it means |
| --- | --- |
| `Running` | Live, nothing observed yet |
| `Uncommitted` | Changes in the checkout that aren't committed |
| `Ready` | Commits ahead of the base, clean tree — deliverable, if UZE cut the branch |
| `Integrating` | Delivery in progress |
| `Conflicted` | A rebase stopped; it stays paused in the agent's own checkout |
| `GateFailed` | The declared gate failed on the rebased commits |
| `Integrated` | The work is in the target |
| `Parked` | The agent is gone and the checkout still holds work |
| `Closed` | The agent is gone and had nothing to deliver |

Only `Ready` and `GateFailed` can be delivered, and only for an isolated
agent: the branch an agent in your own checkout is on is yours, and
rebasing it onto the target and pushing it is yours to ask for. A conflict
returns the task to
the agent that owns it — that agent is the one holding the intent behind the
change — rather than asking you to resolve someone else's rebase.

## Delivery

Delivery is an explicit action (`Alt+I`), one task at a time, under the
repository write lock. uze rebases the branch onto the target's tip **inside the
task's own checkout**, runs the declared gate on the rebased commits, and then
does what `completion:` says:

- **`handoff`** (default) — the branch is left for a person to integrate. Nothing
  reaches the target without someone deciding it should.
- **`merge`** — the target is fast-forwarded, once the gate passes.
- **`pr`** — the branch is pushed and a pull request opened through `gh` (or a
  merge request through `glab`), whichever is on `PATH`.

A failed gate or a conflict leaves the target untouched.

## Work that outlives its agent

An agent can end with commits still on its branch — you closed the tab, the
harness exited, the machine rebooted. That task becomes **parked**, and its
checkout is not handed to anyone else. `Alt+P` opens the preserved list, where
each entry can be:

| Key | Action |
| --- | --- |
| `r` | Resume — start a new agent in that same checkout, on the same branch |
| `i` | Deliver it now |
| `f` | Finish — close the task and free the slot, leaving the branch |
| `d` then `y` | Discard. The one action that destroys work, so it is the one that asks twice |

## Prompt history

What you send to an agent tab is recorded per workspace, and the management view
lists it — click an entry to jump back to the tab it was typed in.

It is a convenience log, not a transcript: uze forwards keystrokes to a
pseudoterminal whose contents it never interprets, so it cannot see what the
agent's own line editor did with them. Entries can be missing, and nothing treats
the history as a complete record. The file is owner-only, and a workspace's
history can be cleared outright.

## The Git extension

The workspace's Git surface is a built-in [extension](/docs/architecture#the-supporting-crates):

- a **commit timeline** in the sidebar, showing what has landed in the target and
  what is still ahead;
- a **changes overlay** (`Ctrl+G`, or the git button in the tab strip) with the
  changed files and a syntax-highlighted diff of the selected one (ADR-039), read
  from the active tab's own working directory.

It is read-only: viewing changes and history, never staging or committing.

Every Git read the workspace makes runs on a thread and answers through a
channel, so nothing it draws waits on a repository — a large history never
blocks a keystroke.

## Subagents inside a session

A harness that spawns its own writing subagents can still collide with itself.
uze projects a small managed region into the project's `AGENTS.md` describing
the checkout the agent is already in, so a subagent knows not to isolate a
second time on top of it, and knows to commit on its own branch instead of
integrating its work itself.

That projection is the only thing this feature writes into your project, and it
lives in its own delimited region — see [Project context](/docs/concepts/context).
